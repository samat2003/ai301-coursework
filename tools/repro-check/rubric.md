# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | Repro report's environment record, compared with the issue's target version, platform, runtime, build, shell, driver, or other named trigger. | The report names the tool version and the platform plus any setting essential to triggering this issue. A different version or trigger-relevant setting is identified and its effect on the result is explained or limited. A difference is material when the issue or thread ties it to the failure, or it changes the input path being tested; an unrelated OS difference by itself does not fail. | required |
| steps-followable | Repro report's starting state, inputs, configuration, commands or UI actions, compared with the issue's trigger. | A stranger can recreate the tested state and perform the trigger from the posted package, including an exact input already shown in the issue and clearly referenced by the report. Supply the input and commands or equivalent concrete UI actions where needed. A private repo, undisclosed config, omitted driver, or skipped trigger fails when the reader cannot rerun the attempt. A concise complete report passes. | required |
| behavior-matches | Report's actual output, logs, screenshots, or observations compared with the issue's reported error or symptom and expected behavior. | The artifact shows the issue's specific failure, or shows the absence of that failure in a clearly identified cannot-reproduce attempt. An adjacent error, an ordinary validation failure instead of a crash, a healthy screen instead of a blank one, or a different exit outcome does not establish reproduction. Do not infer a failure from the report's label alone. | required |
| outcome-honest | Report's reproduced/cannot-reproduce conclusion and material claims about runs, versions, platforms, scope, and cause, read against its artifacts and the issue context. | The conclusion does not exceed what the shown attempt establishes. An evidenced cannot-reproduce passes when it states the limits and relevant differences. For repeated attempts, a representative artifact and a specific, bounded summary of the remaining results can support the claim without pasting every identical output; an unsupported blanket claim cannot. Cross-platform or root-cause claims need evidence for that broader scope. A hypothesis clearly labeled as such is fine. | required |
| claim-specific | Candidate claim comment read against the issue's error or symptom, the report, and the issue thread. | The comment identifies this issue's concrete symptom or trigger and states a realistic next step or intent. It does not substitute generic assignment language, promise a fix or deadline, or claim certainty beyond the report. | required |
| repo-conventions | Repo-facts bug-report and contribution policies, including any AI-use rule, compared with the candidate claim and repro comments. | The comments meet explicit rules that apply to them. In eval mode, treat candidate comments as AI-assisted work when applying a disclosure policy; in live mode, use the student's actual AI use. If the repo requires disclosure, the comments state the tool and extent of assistance as required. A permissive policy or no stated disclosure rule needs no disclosure. AI assistance alone does not mean a comment is fully AI-generated. Apply content requirements for useful evidence, not rigid template formatting. | required |

## Verdict rule

Accept only if every required check passes. Reject if any required check fails or is unclear because its evidence is missing. In live claim-only mode, omit checks needing the not-yet-written repro report from the verdict as SKILL.md directs. The verdict is `accept` or `reject`.
